# 公開済み記事の見直し手順（軽いチェック）

**目的**：公開済み記事の改善点の洗い出し。記事は**編集しない**（指摘リストを作るだけ）。直すのは執筆専任チャット。
**予算**：1バッチ6本、ツール呼び出しは**合計40回以内**、出典URLはネットで開かない（記事と手元のファイルだけで判断する）。

## 読むもの（この順）

1. `docs/ARTICLE-AUDIT.md`（機械チェックの結果。対象の節だけ。誤検出を含む）
2. `docs/HANDOFF-CHAT.md` の「作業ルール」「記事の書き方（絶対に守ること）」の節（方針）。特に：出典で確認できる事実だけ／複数説は併記／「正しい」と書かず仕組みと理由で書く／価格は公式の**税込明記のみ**／効能の断定禁止／ランク（S/A/B/C）は記事に使わない
3. `docs/audit/slug-index.txt`（全公開記事の slug・種別・地域・タイトル。内部リンク提案に使う）
4. 対象の記事（`src/content/en/` 配下）。ダイジェストではなく全文を読む

## 記事ごとのチェック項目

- **A. 根拠**：数字・年・固有名詞・断定のうち、帰属（「〜によると」）も `sources` の裏づけも見えないもの／記事内の矛盾（節ごとに数字が違う）／複数説があるのに一つに決めている／「日本一・最古・最大」で選定主体が無い
- **B. 方針違反**：税込の明記がない金額を本文に載せている（同じ段落に「税込／including tax」があるか。「税込の記載がない」と言いつつ金額を載せるのも違反）／優劣・「正しい」の書き方／効能の断定／ランク表記／AIへの指示のような文
- **C. 鮮度**：料金・営業時間・運行・日程に確認日があるか／"currently / now / this year" など日付のない現在形／`pricesCheckedOn`・`updatedDate` との整合
- **D. 読みやすさと読者価値**：冒頭で結論と使い道が分かるか／FAQ が読者の実際の疑問に答えているか／冗長・回りくどい・曖昧な文／英語として不自然な箇所（箇所と理由だけ。書き直し案は不要）／**公開本文に残った作業メモ口調**（"I saw a search summary…"、"not on this page yet"、"I could not find …" の連発など）
- **E. 内部リンクの機会**：`slug-index.txt` から、話題が深く関係するのに本文からリンクしていないページを**最大5つ**（slug、挿入に自然な段落または見出し、理由）。**食（eat）⇔温泉（soak）の結びつきは方針**なので、地域が重なる記事を優先。`slug-index.txt` にあるものだけ使う
- **F. 他記事との整合**：同じ事実を扱う別記事と食い違いそうな点があれば、該当記事を**1本だけ**開いて確認（記事ごとに最大1本。無ければ書かない）

## 出力

`docs/audit/batch-NN.md` に Write で書く（日本語）。形式：

```
# 見直しバッチN（2026-10-13）
## <記事のパス>
- 総評（1〜2行）: 読者に実害のある点があるか、全体の質
- [high|mid|low] <A〜F> — <指摘（該当箇所の短い引用つき）> — <改善案（1行）>
- 内部リンク候補: /en/... （どの段落に、なぜ）
```

- 重要度：**high**＝読者に誤りや実害／方針違反、**mid**＝直した方が良い、**low**＝好み・軽微
- **指摘が無い項目は書かない**（水増ししない）。1記事あたり指摘は最大12件。具体的に（引用付き）
- 末尾に、このバッチ全体の共通傾向（まとめて直せるもの）を3行以内

## 報告（5行以内）

保存パス、各記事の high 件数、最も重要な指摘2つ、使ったツール呼び出し数。
