### 作業ルール（最優先）

- **1回の指示＝1実行。終わったら報告して一時停止し、GOを待つ。** 村瀬さんが実行ごとに利用量を確認する。勝手に次を始めない
- **調査エージェントは1回に1系統だけ。並行させない。** 2026-10-10 に5系統並行で走らせてセッション上限（429）に当たった。調査は「ハブ＋系譜2本」程度に範囲を絞る
- **調査結果はすぐ `docs/research/<品目>-<日付>.md` に出典つきで保存**し、執筆はメモから行う。調査と執筆は別の実行に分けてよい
- 壁打ち → 提案 → 「実装しますか？」で承認を得てから実装。ただし系譜ページの執筆はこの型で承認済みなので、GOが出たら書いてよい
- 村瀬さんが同じリポジトリを並行して触る。`git add -A` は使わず、変更したファイルを明示して add する。push 前に `git fetch && git rebase --autostash origin/main`（為替ボットのコミットが日次で入る）
- 作業ツリーに村瀬さん側の未コミット変更（`src/pages/[lang]/food-prices.astro`、`src/assets/`）がある。触らない・コミットに含めない
- コミット末尾に `Co-Authored-By: <使っているモデル名> <noreply@anthropic.com>` を付ける
- 記事の description は **160字以内**（`npm run check` で落ちる）。FAQ の答えに「: 」（コロン＋空白）を入れない（YAML が壊れる）

### 記事の書き方（絶対に守ること）

- **出典で確認できる事実だけ書く。** 調査で「未確認」のものは書かない。記憶の年号・価格を出さない。起源に複数説があれば両方を併記して決めない
- 「正しい食文化」は **「仕組みと理由」に翻訳して書く。** "the correct way" と書かない。なぜそうか・日本人はどうしているか・いくらか、を書く。正しさが一つでないもの（だしの東西、割下の有無）はそう書く
- 系譜ページは固定10項目：起源／定義する要素／土地との関係／店の型と値段／注文と食べ方／地域差・派生／本場で食べる・行き方／**本場と出先の違い**（東京・大阪で食べるとどう違うか。村瀬さんの指示で追加）／誤解／出典。見出しは既存記事の英語見出しをそのまま使う
- 価格は本文に手書きせず `<DishPrices keys={[...]} />` で基準価格ページのデータを出す。固有店の価格は公式サイトで確認できた税込のみ、確認日つき
- 系譜の横並び表は `src/data/lineages/<dish>.json` に持ち、ハブは `<LineageTable dish="..." />` で描く。記事が無い系譜は `status: "planned"`、出典の無い年代は `"—"`
- frontmatter：`kind: dish | lineage`、`dish`、`lineage`（slug は `<dish>-<lineage>`）、`basis: researched`、`sources` 2本以上

### 調査エージェントへの指示の型

既存記事の出典の質を保つため、調査プロンプトには必ず入れる：
「出典が確認できる事実だけ。各事実に実際に開いたURLを [n] で添え、最後に出典一覧。開けなかったURL・検索要約だけの情報・記憶の数字は使わない。個人ブログ・食べログ・Wikipedia は使わず一次資料を辿る。出典の優先順位：省庁（農水省『うちの郷土料理』、統計局家計調査）＞業界団体・博物館＞自治体・観光連盟＞店の公式＞新聞。起源の複数説は両方。価格は公式の税込のみ。本場と出先の違い（東京・大阪で食べるときの差）を必ず1項目入れる。」

### 気をつけること（実際に起きた失敗）

- 調査を5系統並行で走らせて利用量の上限に当たった（上記）
- description が160字を超えて `npm run check` で落ちる。書く前に文字数を数える
- FAQ の答えに「: 」があると YAML が壊れてビルドが落ちる
- Bash のヒアドキュメントでコードを生成すると壊れる。ファイルは Write ツールで書く
- 系譜データ（JSON）に記憶の年代を入れかけた。出典が付くまで「—」
- 以前の失敗：自動取得が札幌の値を全国平均として書いた／デモ記事に事実誤りがあった。黙って代替しない、外部仕様は出典を持たせる

## モデルの選び方（村瀬さんへの助言）

- **執筆（系譜ページ）は Opus 推奨。** 英語の文体と「出典だけで書く」規律を保つのが仕事の中心で、ここが落ちると記事の価値が落ちる
- **調査エージェントは Sonnet で足りる。** 公式サイトを開いて事実とURLを拾う作業は Sonnet 向きで、消費も少ない。Agent ツールの `model: "sonnet"` で指定できる
- Sonnet だけで進める場合は、執筆後に「出典に無い数字が入っていないか」「description の長さ」を一度 Opus で確認すると安全
